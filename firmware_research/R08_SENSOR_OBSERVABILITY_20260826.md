# R08 三轴传感器实机可观测性记录（2026-08-26）

## 结论

目标戒指 `R08_9C07 / 31:31:45:37:9C:07` 的当前官方固件确实能通过 Nordic UART 通知输出三轴加速度，但 `A1 04 04` 原始测量模式下的实测输出频率只有约 **0.994 Hz**。转动造成的 X/Z 轴变化足够明显，说明部分姿态变化可以观察；这个频率仍比连续滚动所需的 50 Hz 左右低约 50 倍，不能直接实现跟手滚动。

因此后续固件工作的重点不是继续调 Windows 滚轮参数，而是：

1. 将 LIS3DH 采样和姿态处理提高到至少 50 Hz；
2. 把加速度计从当前包含光学通道的 `A1 04 04` 测量流程中拆开，避免绿灯和不必要耗电；
3. 在戒指端计算经过死区、滤波和速度限制的滚动增量，再以较低 BLE 包率批量发送；
4. 双击后才由 Windows 显式进入高频模式；当前离线候选每 8 秒续期、固件 12 秒无续期硬停止并回到低功耗模式。

## 安全边界

- 本次没有调用 DFU Start/Init/Data/Check/End，也没有刷写固件。
- 只发送了已知 UART 命令 `A1 04 04`，结束时成功发送 `A1 02`。
- 采集结束日志明确记录 `SENSOR_STOP_REQUESTED 已发送 A1 02`。
- 当前只有一枚戒指，恢复入口仍未验证，因此本报告不授权把实验镜像刷入戒指。

## 现场环境与连接结果

- Windows 最初保存的 R08 GATT 会话已失效，Win32 写入和通知配置均返回 `0x80070079`。
- 精确移除了 R08 主节点和 6 个地址为 `313145379C07` 的服务缓存；未操作 NuPhy 键盘。
- 定向重启了 `Intel(R) Wireless Bluetooth(R)` 适配器。
- 受限进程中的 WinRT 连接返回 `0x80004005`；管理员完整桌面进程随后成功建立 GATT 会话。
- 成功连接时 Windows 报告 GATT 会话为 `ACTIVE`，MTU/PDU 大小为 247。
- HID 服务 `0x1812` 在未配对会话中被 Windows 标记为 access denied，但 Nordic UART 服务可正常通知和写入。

| 首末样本跨度 | 20.125 s |
| 有效频率 | 0.9938 Hz |
| 平均间隔 | 1006.25 ms |
| P95 间隔 | 1203.25 ms |

| Y 范围 | -268 ～ -72（跨度 196） |

每个周期同时收到一组五通道通知：

| 通道 | 数量 | 当前解释 |
| --- | ---: | --- |
| `A1 01` | 21 | 光学/血氧原始数据 |
| `A1 02` | 21 | 心率 PPG 原始数据 |
| `A1 03` | 21 | LIS3DH 三轴加速度 |
| `A1 04` | 21 | 未知测量辅助通道，当前值多为零 |
| `A1 05` | 21 | 未知测量辅助通道 |

这说明当前约 1 Hz 的限制很可能来自上层测量打包定时器，而不一定是 LIS3DH 硬件本身的最高采样率。仅提高 UART 通知频率还不够，必须继续定位 LIS3DH ODR 配置、读取循环与 `A1` 五通道打包任务。

后续离线分析修正了早期对两个字符串相邻值的判断。`0x00835A63` 与 `gsensor_read_timer_id` 一起作为参数传给 ROM timer 创建函数 `0x00011634`，对应 timer 对象 `0x0020BF80`；`0x00835A0B` 与 `gsensor_shake_flag_timer_id` 一起传入，对应 `0x0020BF84`。两个奇数值本身落在既有计算函数中段，直接从该地址执行会缺少函数序言和寄存器上下文，因此不能当作普通回调入口；更准确的定性是 timer ID/上下文参数。Realtek 官方 OS timer FAQ 确认周期参数单位为毫秒、最小精度为 10 ms，因此创建参数 `2000`、后续 `800` 和 `3000` 分别对应约 2 秒、0.8 秒和 3 秒。

真正的 `A1` 链已经定位：主命令分发在 `0x0082D0E4` 比较 `0xA1`，经 `0x0082D190` 调用处理器 `0x008280B4`；`A1 04` 分支进入 `0x008281D0`，并在 `0x00828240` 以回调/上下文参数 `0x00829DAB`、周期参数 `0x7D << 3 = 1000`、重复标志 `1` 调用 `0x00829F18`。该包装函数内含 `qc_timer_restart` 字符串，并调用底层 ROM timer API。官方 API 语义和实测共同确认这里是约 1000 ms 的上层周期。

`0x00827DAA` 已确认依次构造 `A1 01..05` 五个 16 字节通知包：校验统一调用 `0x0082AC00`，发送统一调用 `0x0082E974`。下一步应解释定时上下文 `0x00829DAB` 如何回到该打包函数，而不是继续从字符串名猜测回调。

进一步交叉引用显示，`0x00827DAA` 的唯一直接 `bl` 调用在 `0x008282EA`，即 A1 处理器的公共尾部。`0x00829DAB` 作为 `0x00829F18` 的附加 timer 参数保存；把它按 Thumb 地址 `0x00829DAA` 反汇编会落入低层硬件例程中段，后续依赖既有寄存器/栈上下文，没有独立函数入口，也不直接调用 `0x00827DAA`。因此 timer 到打包器之间仍存在尚未恢复的事件/队列分发；不能简单修改 `1000` 就声称只提高 `A1 03` 帧率，因为现有公共尾部会同时打包 `A1 01..05`，可能连带提高光学测量、LED 占空和功耗。

LIS3DH 的硬件配置和缓冲链也已经定位：

- 活动采样窗口的 FIFO 路径 `0x00832D06 -> 0x00832D22` 通过 `0x00832928` 写 `CTRL_REG1 0x20 = 0x37`，即 25 Hz、X/Y/Z 全部开启；随后把 `FIFO_CTRL_REG 0x2E` 先写 `0x00`，再写 `0x80` 进入 stream 模式。
- 另一条 `0x008335FC -> 0x0083368C` 路径才写 `CTRL_REG1 0x20 = 0x47`（50 Hz）。该分支同时写 `CTRL_REG2=0x31`、`CTRL_REG3=0x40`、`INT1_CFG=0x2A`、`INT1_THS=0x1F`、`INT1_DURATION=0`，即高通滤波和三轴正向阈值的 INT1 待机动作/唤醒检测配置；它关闭 FIFO，不能视为全局连续采样模式。
- `0x00832F9C` 是按已识别传感器型号分支的批量读取函数；LIS3DH 路径先读取 FIFO 状态寄存器 `0x2F`，把样本数上限限制为 32，再在内部循环 `0x00833120` 从输出首寄存器 `0x28` 每次连读 6 字节。
- 这些 6 字节 XYZ 样本被写入 `0x0020BF70` 附近的环形缓冲；`0x0083394E` 再从缓冲中取出三轴值，供 `A1 03` 打包。

`0x008337D4` 状态机也支持上述区分：INT1/活动事件路径在 `0x00833C88` 设置状态 `+5`，handler 在 `0x00833822` 调用 `0x00832D06` 开始 25 Hz FIFO，并对 `0x0020BF80` timer 使用 `800`（800 ms）的 restart 参数；后续没有特殊状态时在 `0x0083386A` 周期调用 `0x00832F9C` 排空 FIFO，状态 `+4` 则进入停止路径。25 Hz × 0.8 秒约为每周期 20 个样本，低于 32 样本 FIFO 深度，与周期排空相符。

`0x00833CF0` 的创建参数还显示：read timer `0x0020BF80` 的 repeat 参数为 `1`，shake timer `0x0020BF84` 的 repeat 参数为 `0`。这与前者周期排空 FIFO、后者在 `02 02` 后做一次性门控/冷却的控制流一致。

另一路加速度算法已和真机通知对上：`0x00833A7C` 处理 XYZ 后，在判定结果连续超过 `2000`、计数超过 10 次时调用 `0x0082D408(2)`。`0x0082D408` 构造 16 字节包，前两字节为 `02 02`，校验调用 `0x0082AC00`，通知调用 `0x0082E974`，最终正是实测的 `02 02 00 00 00 00 00 00 00 00 00 00 00 00 00 04`。发送后代码以 `3000`（3000 ms）重启 timer 对象 `0x0020BF84`（`gsensor_shake_flag_timer_id`）并设置门控标志；因此它对应这条 shake/敲击动作的约 3 秒门控或冷却期，而非 FIFO 排空周期。

因此现在可以确认：25 Hz FIFO 连续采集、50 Hz INT1 动作检测、硬件 FIFO 批读、RAM 缓冲消费和 `A1` BLE 通知是不同速率层。真机约 `0.994 Hz` 只证明当前公开通知层约 1 Hz，不能再解释为加速度计只以 1 Hz 工作；尚未独立量化的是 FIFO 被排空以及环形缓冲实际被填充的频率。

## 对转动滚动的硬件限制

官方镜像中已发现源码路径字符串 `qc_code\\app_module\\gsensor\\lis3dh_spi.c`，尚未发现陀螺仪型号证据。三轴加速度可以利用重力方向估计俯仰和横滚，例如：

- `roll = atan2(y, z)`
- `pitch = atan2(-x, sqrt(y² + z²))`

但加速度计无法观察绕重力方向的纯旋转。因此可实现的是与佩戴姿态有关的“倾斜/翻腕滚动”，不能承诺任意姿势下像旋钮一样识别纯轴向旋转。

## 与 ATC_RF03_Ring 的关系

`ATC_RF03_Ring` 提供的是 BlueX RF03、STK8321 加速度计的 R02/RY02 固件和 OTA 资料。R08 内层镜像已由 Realtek 应用头、`ic_type=12` 和 `0x0020xxxx` RAM 地址确认属于 RTL8762E 系列，并使用 LIS3DH；两者不是同一 SoC。该项目只能参考逆向方法和相似的 QRing 外层包装，不能复用 RF03 内存布局、STK8321 驱动或现成固件。

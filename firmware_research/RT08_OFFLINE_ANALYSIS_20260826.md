# RT08 固件离线分析记录（2026-08-26）

## 当前结论

已经确认 `RT08_3.10.48_260309.bin` 是 `RT08_V3.1` 的官方 OTA 应用镜像，并在不连接戒指、不发送 DFU 的前提下定位到触控/戒指手势配置命令 `0x3B` 的实际处理链：

```text
命令分发 0x0082D092
  └─ 命令 0x3B → 0x0082D12E
       └─ 处理函数 0x0082C994
            └─ 手势配置写入 0x00834144
```

APK 与固件逐字节对照确认存在一个字段错位：

- QRing 的 `TouchControlReq.getWriteInstance(..., false, strength, ...)` 把手势强度放在完整 16 字节数据包的偏移 `4`；
- 固件 `0x0082C994` 原本把强度硬编码为 `1`，并从偏移 `5` 读取另一个字段；
- 随后的 `0x00834144` 明确把结构体第 2 个字节限制在 `1..10`，说明这里确实是可调强度字段；
- QRing 的 `showStrengthSelectionDialog` 把用户选中的 `1..10` 数值传入上述请求，因此 APK 与固件在这个字段上不一致。

这能解释“App 有强度选择，但戒指灵敏度没有实际变化”的现象。它不能单独实现连续转动滚动。

补丁地址为 `0x0082CA54`，文件偏移为 `0x6AA4`：

```text
原指令字节：4B 74 60 79 88 74
新指令字节：20 79 48 74 8E 74
```

反汇编语义从：

```text
strb r3, [strength]       ; 固定写 1
ldrb r0, [packet, #5]     ; 读取 APK 没有填写的后一个字节
strb r0, [flag]
```

变为：

```text
ldrb r0, [packet, #4]     ; 读取 APK 实际发送的 1..10 强度

strb r6, [flag]           ; 保持原请求的默认 0
```

二进制比较只有 6 个不同字节：5 个业务指令字节，以及头部偏移 `0x0C` 的 1 个 sum32 校验和字节。实验镜像的 payload 长度仍为 `146732`，重新计算后的 sum32 为 `13582184`，检查器确认头部、长度、sum32、硬件和固件标记全部一致。

## 已排除的误判

`0x00835962` / `0x00835A86` 的传感器滤波与角度归一化逻辑被 4 处 `0x69` 数据包路径调用。APK SDK 明确把 `0x69` 定义为心率、血氧、血压、体温等测量命令，因此这条链属于测量姿态/佩戴状态相关数据，不应直接当作戒指转动手势来修改。

触控命令 `0x3B` 的子类型 `2` 在当前 APK 中主要由 `MuslimActivity` 的触控休眠功能使用；`RingGestureActivity` 使用的是子类型 `1`。因此不能再把子类型 `2` 未处理直接解释为 RingGesture 双击唤醒失败。

## 连续转动滚动仍缺少的证据

当前实验补丁只让已有 `1..10` 手势强度参数真正生效。要实现“转动戒指连续滚动”，仍需定位并验证以下任一数据源：

1. LIS3DH 三轴加速度的稳定高频采样链，并证明目标转动轴可以由重力方向变化观测；
2. 触控芯片的连续坐标/位移数据，而不只是完成后上报 `0x1D` 的离散动作 `1/2/3`；
3. 若硬件实际包含陀螺仪，则确认其型号、寄存器和采样路径。

目前镜像只出现 `lis3dh_spi.c`，尚无陀螺仪型号证据。仅有加速度计时，绕重力轴的旋转不可观测，所以不能承诺任意佩戴姿态下的连续旋转滚动。

## A1 原始传感器定时链补充

已在官方镜像中定位到 `A1 04 04` 的上层处理和五通道打包链：

```text
命令分发 0x0082D0E4 (cmp 0xA1)
  └─ 0x0082D190 -> A1 处理器 0x008280B4
       └─ 子命令 0x04 -> 0x008281D0
            └─ 0x00828240 -> timer 包装 0x00829F18
                 r1 = 0x00829DAB
                 r2 = 0x7D << 3 = 1000
                 r3 = 1

五通道打包 0x00827DAA
  ├─ A1 01
  ├─ A1 02
  ├─ A1 03（三轴）
  ├─ A1 04
  └─ A1 05
       校验 0x0082AC00
       通知发送 0x0082E974
```

`0x00829F18` 的初始化路径使用字符串 `qc_timer_restart`，并调用 ROM 地址 `0x00011634` / `0x00011670`；已存在 timer 时通过 `0x00011694` 以新周期重启。Realtek 官方 OS timer FAQ 明确该 API 的周期参数单位为毫秒、最小精度为 10 ms；因此这里的 `1000` 就是约 1000 ms，并与真机约 0.994 Hz 相互印证。

交叉引用进一步限定了这条链：`0x00827DAA` 的唯一直接 `bl` 调用位于 `0x008282EA`，即 A1 处理器的公共尾部。`0x00829DAB` 被作为 `0x00829F18` 的额外 timer 参数保存；若把奇数 Thumb 地址还原为 `0x00829DAA` 并直接反汇编，会落在低层硬件例程中段，既无独立函数序言，后续又依赖先前的寄存器和栈内容，也没有通向 `0x00827DAA` 的直接调用。因此它仍应视为 timer ID/上下文，而不是已证明的普通回调入口。

这意味着 `1000` 不是可以直接缩短的安全“BLE 帧率旋钮”。尚未恢复的 timer 事件/队列很可能重新进入 A1 处理器，而公共尾部一次会发送 `A1 01..05` 全部五个通道。若直接把它改成 50 或 100，可能同时提高光学测量与 LED 占空、显著增加功耗；正确候选应在恢复间接分发后，为 `A1 03` 或新的 IMU-only 通知建立独立节拍。

两个 gsensor timer 的创建链也已找到：

```text
timer object 0x0020BF80
  name/context: gsensor_read_timer_id / 0x00835A63
  create period: 2000

timer object 0x0020BF84
  name/context: gsensor_shake_flag_timer_id / 0x00835A0B
  create period: 2000
```

`0x00835A63` / `0x00835A0B` 确实作为附加参数传给 ROM timer 创建函数，但它们落在既有计算函数中段，不具备独立函数入口的序言和上下文，因此不能当作可执行回调地址；目前应称为 timer ID/上下文参数。状态机后续还分别出现 `800` 和 `3000` 的 restart 参数；结合 Realtek 官方 API 语义，它们分别是约 800 ms 和 3000 ms，但仍不能脱离各自状态机直接修改。

进一步恢复 `0x00833CF0` 的创建参数后，可以区分两个 timer 的运行方式：

```text
0x0020BF80 / gsensor_read_timer_id
  create period = 2000
  repeat 参数 = 1
  活动阶段 restart = 800

0x0020BF84 / gsensor_shake_flag_timer_id
  create period = 2000
  repeat 参数 = 0
  发出 02 02 后 restart = 3000
```

ROM API 的具体符号名尚未从本机镜像恢复，但 Realtek 官方 API 文档已确认时间单位为毫秒；同一调用约定下的 `1/0` 差异、后续控制流和 timer 名称一致支持：`0x0020BF80` 是周期 read timer，`0x0020BF84` 是一次性 shake 门控 timer。

read timer 最主要的状态转换位于 `0x008337D4`，状态结构从 `0x0020BFA0` 开始：

| 状态字节 | 设置/处理位置 | 静态控制流含义 |
| --- | --- | --- |
| `+3` | `0x008338C8` / `0x008337DC` | 初始化请求：配置 FIFO 后转入待机配置阶段 |
| `+4` | `0x008338E8` / `0x008337FC` | 停止请求：停止 read timer、关闭当前传感器路径 |
| `+5` | `0x00833C88` / `0x00833822` | INT1/活动事件：配置 25 Hz FIFO，并以 `800` 重启周期 read timer |
| `+6` | `0x008337F0` / `0x00833846` | 切回 50 Hz INT1 待机配置；成功后停止 read timer |
| 无特殊状态 | `0x0083386A` | 调用 `0x00832F9C` 批读/排空 FIFO |

因此活动读取闭环是：INT1/活动事件设置 `+5`，timer handler 配置 25 Hz FIFO 并保持 800 ms 周期；后续普通周期进入 `0x0083386A` 排空 FIFO；收到 `+4` 后走停止路径。此前把 `800` 只描述成“一次 0.8 秒采样窗口”过于保守，更准确的静态结论是它控制周期读取阶段，活动阶段能持续多个周期，直到显式停止状态到达。

## LIS3DH 的 25 Hz FIFO 与 50 Hz 动作检测配置

设备型号分派函数 `0x00832D06` 对目标 LIS3DH 分支（设备类型 `0x11` / `0x28`）进入 `0x00832D22`，执行：

```text
movs r1, #0x37
movs r0, #0x20
bl   0x00832928
...
movs r1, #0
movs r0, #0x2e
bl   0x00832928
movs r1, #0x80
movs r0, #0x2e
bl   0x00832928
```

`0x00832928` 是寄存器写函数，成功返回 `1`。按 LIS3DH 定义，`CTRL_REG1 0x20 = 0x37` 是 25 Hz、XYZ 全开；`FIFO_CTRL_REG 0x2E` 先写 bypass `0x00` 再写 stream `0x80`。同一分支还写 `CTRL_REG4=0x90` 和 `CTRL_REG5=0x40`，后者明确打开 FIFO。这是当前已定位的活动采样窗口配置，不代表固件让 FIFO 永久运行。

另一函数 `0x008335FC` 也是设备型号分派，但只在 `0x008337D4` 状态机的特殊分支中由 `0x00833850` 调用。目标 `0x28` 分支在 `0x0083368C` 执行：

```text
movs r1, #0x47
movs r0, #0x20
bl   0x00832928
```

这里的 `CTRL_REG1 0x20 = 0x47` 表示 50 Hz、XYZ 全开。关键是同一分支随后还写入：

```text
CTRL_REG4     0x23 = 0x88
CTRL_REG2     0x21 = 0x31
CTRL_REG3     0x22 = 0x40
CTRL_REG6     0x25 = 0x00
CTRL_REG5     0x24 = 0x00
INT1_CFG      0x30 = 0x2A
INT1_THS      0x32 = 0x1F
INT1_DURATION 0x33 = 0x00
```

这组寄存器打开高通滤波，将 AOI1 路由到 INT1，并对 X/Y/Z 正向高阈值事件进行检测；同时关闭 FIFO。它是待机动作/唤醒检测配置，不是 FIFO 连续采样配置。真机约 1 Hz 的 `A1 03` 依然不是 LIS3DH 硬件 ODR 上限，但也不能据此声称已有 50 Hz 连续样本流。

数据路径为：

```text
LIS3DH CTRL_REG1 = 0x37（25 Hz）+ FIFO stream
  -> 批量读取函数 0x00832F9C
       -> 读取 FIFO_SRC_REG 0x2F，样本数最多 32
       -> 内部循环 0x00833120 从寄存器 0x28 每次连读 6 字节 XYZ
            -> 0x0020BF70 附近 RAM 环形缓冲
                 -> 0x0083394E 取样
                      -> 0x00827DAA 构造 A1 03
                           -> 0x0082E974 BLE 通知（当前约 1 Hz）
```

`0x00832F9C` 的直接调用点至少包括 `0x00833254`、`0x0083386A` 和 `0x00833962`：第一处位于配置/初始化函数，第二处是周期 read timer 无特殊状态时的 FIFO 排空路径，第三处位于缓冲读取入口。活动事件分支调用 `0x00832D06` 开始 25 Hz FIFO，并以 `800` 参数（即 800 ms）重启 timer `0x0020BF80`；后续普通周期反复进入 `0x0083386A`，直到停止请求或切回 INT1 待机。25 Hz × 0.8 秒约为每周期 20 个样本，低于 FIFO 的 32 样本上限，和周期排空吻合。

后续分析已确认环形缓冲的 16 位生产者字节计数位于 `0x0020BFA8`，每个 XYZ 样本前进 6，容量阈值为 `0x1EC` 字节（82 个样本）。当前 IMU-only 候选每 100 ms 比较该计数：只有生产者前进才发送有效样本；未前进则只发送一次 `STALE`，随后停止 timer、FIFO 和传感器。活动阶段还受候选 12 秒硬超时及主机 8 秒续期约束。当前证据支持“25 Hz FIFO 周期读取 + 50 Hz INT1 待机动作检测”两种配置，不能写成固件持续向 RAM 写入 50 个独立样本/秒。

## `02 02` 的 gsensor 生成链

`0x00833A7C` 从 RAM 缓冲处理 XYZ。目标 `0x28` 分支调用 `0x0084589C` 做姿态/强度计算，随后在门控允许时调用 `0x008459A4`，将结果与 `0x7D << 4 = 2000` 比较。结果连续超过阈值、计数超过 10 次后执行：

```text
movs r0, #2
bl   0x0082D408
ldr  r1, =3000
ldr  r0, =0x0020BF84
bl   0x00011694
```

`0x0082D408` 将包首字节写为 `0x02`、第二字节写为传入的 `0x02`，调用 `0x0082AC00` 计算末字节校验，再通过 `0x0082E974` 通知。它与真机日志逐字节一致：

```text
02 02 00 00 00 00 00 00 00 00 00 00 00 00 00 04
```

因此这个“相机/遥控”事件至少有一条明确的 IMU/敲击生成路径；不能再默认它只来自触控区。`0x0020BF84` 正是创建时关联 `gsensor_shake_flag_timer_id` 的 timer，发送后设置门控标志并以 `3000`（3000 ms）重启，符合动作冷却/防重复触发。

## 真实触摸区事件与 `73 2A` 状态链

后续离线分析定位了独立于上述 `02 02` 加速度路径的触摸芯片读取链。按本仓库统一的运行地址换算，`0x00834512` 通过触摸芯片接口读取寄存器 `0xA7`，并把硬件返回值转换为动作码后写入 `0x0020C1A8 + 1`：`0xB4` 映射为 `2`，`0xB5/0xB6/0xB7/0xB9` 映射为 `3`，其他有效值映射为 `1`。这条路径读取的是戒指触摸区域，不是 LIS3DH 加速度冲击。

触控事件状态机随后会进入 `0x0083470A` 附近的分派逻辑；物理触摸事件分支调用触摸读取及状态更新函数。通知构造函数 `0x0082D2AE` 生成固定 16 字节包：首字节 `0x73`，第二字节为传入子命令，第三字节为状态值，末字节为校验和。真机日志已经捕获戒指主动上报：

```text
73 2A 01 00 00 00 00 00 00 00 00 00 00 00 00 9E
```

后续对时间线复核发现，即使用户完全没有触摸，`73 2A 01` 也会在配置的一分钟到期附近出现。因此该包来自真实触摸子系统并不等于它代表“刚刚双击”；状态含义应为 `73 2A 00=唤醒`、`73 2A 01=休眠`。此前所谓“首次触摸唤醒真机验证”是把自动休眠误判成唤醒，现已撤回。`02 02` 仍明确忽略。由于官方 `3B` 会让 Windows 当前 GATT 对象关闭，v7 IMU 组合模式不主动开启原厂触控，而是使用两次独立 IMU 冲击作为主机侧唤醒源；这不能证明敲击发生在电容触控区。

## `50 55 AA` 原厂“查找设备”提示候选

QRing APK 的 `FindDeviceReq` 使用命令头 `0x50`，正文固定为 `55 AA`，经 16 字节补零和加和校验后为：

```text
50 55 AA 00 00 00 00 00 00 00 00 00 00 00 00 4F
```

精确匹配的 RT08 固件在 `0x0082C41E` 比较命令 `0x50`，跳到 `0x0082C602` 的专用处理分支。该分支调用内部提示序列 `0x00829B86`；随后调用的另一个候选接口 `0x0083C7C2` 在本固件中只是 `bx lr` 空函数。这个路径与 `A1 04 04` 光学/血氧原始传感器路径完全分离，因此可以作为非光学“查找设备”提示的受控真机候选。

后续使用非受限的本机 Windows 蓝牙会话已成功发送 `50 55 AA`。用户肉眼确认亮灯位置正是预期的触控区域，而且一次请求约闪烁 20 次；它不是心率/血氧光学灯。`0x50` 分支调用 `0x00829B86` 前将 `r0` 固定为 `0x14`（十进制 20），与真机观察高度吻合，说明这是一段查找设备长提示而不是适合连接状态的短提示。默认连接流程已停止发送它；后续需离线检查同一提示驱动的其他调用点，寻找已存在的短序列或安全停止入口，不得通过重复命令或 `A1 04 04` 冒充实现。

还测试了 QRing SDK 的 `LoverEventReq`，完整数据包为 `51 01 00 00 00 00 00 00 00 00 00 00 00 00 00 52`。精确固件的 `0x51` 分支会调用同一内部提示引擎并使用参数 `8`，但真机发送成功后用户没有看到任何位置亮灯。因此 `0x51` 不能作为连接短提示，运行时诊断入口已删除；不能仅凭内部调用参数推断可见闪烁次数。

## 刷写状态

没有发送 DFU Start/Init/Data/Check/End，没有擦除或写入戒指。当前仍不具备以下条件：

- 独立物理介质上的第二份原厂备份；
- 已验证的 Boot ROM/SWD/JTAG 恢复路径；
- 签名、Secure Boot、反回滚和分区策略结论；
- 第二枚同硬件戒指的首次试刷环境。

因此实验镜像只是离线候选，不应刷入当前唯一设备。
